# Changes of 2026-10-10

What was done, how to use and test it, and what is still open. Covers three things: the `volume` field
in the Rust engine, the rebuilt iOS libraries, and the first phase of preparing the Django backend for Google Cloud Run.

Rule followed throughout: the backend's processing engines (`feedback_generator/`, `hum/`) were not changed.
Only how requests reach them was.

## 1. `volume` on every detected note (Rust, Dart)

Each note the Rust engine emits now has `volume`: **0.0 to 1.0, spaced in decibels** (0.0 is -60 dBFS or quieter,
1.0 is full scale, so every 0.1 is 6 dB). It is the loudest 50 ms inside the note's span.

- It is relative to the microphone and device, not calibrated. Turning it into pp..ff is a job for the backend, using the score's markings.
- It is `null` on score notes.
- Known limit: in legato playing the window can include the previous note's ring-out, so a soft note after a loud one reads high.
- On clips rendered at MIDI velocity 35 to 110, volume correlated 0.85 with velocity. Good for "louder or softer than before", not exact levels.

| Where | Change |
|---|---|
| `native_ffi/src/volume.rs` (new) | The measurement, plus `LevelLog`, a running record of loudness (about 40 values per second) so a long note's attack can still be looked up after the raw audio is gone |
| `native_ffi/src/audio.rs` | Feeds `LevelLog` in both processing loops and sets `volume` on each note before it is published |
| `native_ffi/src/models.rs` and other `Notes` literals | New field `volume: Option<f32>` |
| `native_ffi/src/tracker.rs` | Only `offset_ms` became `pub`; the file is otherwise upstream's version |
| `frontend/lib/src/rust/*`, `native_ffi/src/frb_generated.rs` | Regenerated with flutter_rust_bridge codegen **2.13.0** |
| `Phrase_send2_server.dart`, `Rust_Session.dart` | Send `volume` to the backend and read it back from `getUserData()` (two helpers made `@visibleForTesting`) |
| `native_ffi/examples/dump_json.rs` (new) | Replays a WAV through the real detector and writes the notes as JSON |
| `backend/rust_samples/` (new) | Real detector output and the request built from it, with a README |

The Python backend accepts `volume` and ignores it. No score uses it yet.

Test it:

```bash
cd native_ffi && cargo test                                  # 106 tests
cd frontend   && flutter test                                # includes test/note_volume_test.dart
# Does it follow loudness? Compare each note's volume to how hard it was played:
cd native_ffi && cargo run --release --example dump_json -- \
  fixtures/piano/rendered/05_dynamics_solo.wav fixtures/piano/rendered/05_dynamics_solo.json
```

## 2. iOS static libraries

`frontend/ios/libnative_ffi.a` (device) and `libnative_ffi_sim.a` (simulator) were rebuilt from the current source.
The committed ones were built before `volume` existed: the app would have started and then failed when the first note arrived,
because the old library sends 10 fields per note and the Dart bindings read 11. The bridge's start-up hash check does **not**
catch this, because the hash does not change when a struct field is added.

To rebuild: use codegen 2.13.0 (the pinned runtime version; `build_rs.sh` uses whatever `flutter_rust_bridge_codegen` is on the path), then
`cargo build --release --target aarch64-apple-ios` and `--target aarch64-apple-ios-sim`, and copy the two `libnative_ffi.a` files into `frontend/ios/`.
Check a rebuilt library with `nm -a <lib> | grep -c LevelLog` (it must not be 0).

## 3. Backend, Phase 1: safe to put on the internet

Setup for Google Cloud Run is in [`backend/deploy/README.md`](../backend/deploy/README.md) and the plan is in
[`docs/superpowers/specs/2026-10-10-backend-cloud-run-deployment-design.md`](superpowers/specs/2026-10-10-backend-cloud-run-deployment-design.md).

### Production switch

`server/config.py` builds the settings from the environment. **Development is the default and behaves as before.**
Production turns on when `DJANGO_ENV=production` or `K_SERVICE` is set (Cloud Run sets it itself). In production the server
**refuses to start** unless these are set:

| Variable | Meaning |
|---|---|
| `DJANGO_SECRET_KEY` | A real secret, not the development default |
| `ALLOWED_HOSTS` | Host names, comma separated, no `*` |
| `APP_API_KEY` | The shared key the app sends in the `X-App-Key` header |
| `RATE_LIMIT_HUM_PER_MINUTE` | Optional. Per client; production default 30, development off |
| `RATE_LIMIT_DEFAULT_PER_MINUTE` | Optional. Per client; production default 120, development off |

Production also forces `DEBUG` off and trusts Cloud Run's `X-Forwarded-Proto` header.

### What stands in front of the routes (`server/middleware.py`)

In this order, set in `settings.MIDDLEWARE`:

1. **Health check:** `GET /healthz` answers `ok` with no key, no limit and no host check, for Cloud Run's probe.
2. **Rate limit:** sliding window per client. Clients are told apart by the *last* `X-Forwarded-For` entry (the one Cloud Run's proxy adds). Over the limit gives 429 with `Retry-After`.
3. **App key:** other requests need a matching `X-App-Key`, otherwise 401 with `{"error", "code": "unauthorized"}`.
   Exception: `GET /api/hum/talk/speech/<id>`, which an audio player fetches without our header. The id is 96 random bits and expires, so the URL acts as the credential.

Both checks are off in development unless you set the variables. The key is shipped inside the app, so it discourages casual abuse but can be extracted.

### Other changes

- `/storage/` is served only when `DEBUG` is on (`server/views.py`). In production it is a 404; it holds feedback files.
- `api/urls.py` includes `quiz.urls`, so `/api/quiz/*` no longer returns 404.
- `backend/requirements-prod.txt`: what the deployed server needs, without the old PDF pipeline packages (oemer, OpenCV, pyvips, Tesseract, pdfplumber, PyMuPDF, zeroconf).
  Install with `pip install -r requirements-prod.txt && pip install --no-deps basic-pitch`.
- `backend/.env.example` documents the new variables.

### Test it

```bash
cd backend
python manage.py test server        # 39 tests; needs the production requirements installed
```

These tests do not need a database. Verified in a clean Python 3.13 environment built from `requirements-prod.txt` only.
Also run against a real gunicorn process in both modes: missing production settings refuse to start; with settings, a wrong or missing key is 401,
an unknown host is 400, `/storage/` is 404, the hum limit gives 429 after 30 requests; development has no key, no limit and still serves `/storage/`.

## Known problems and open items

- **Awaited stream cancel never returns** in a host test of the Rust bridge, with the old and the new Rust alike, so it predates this work.
  The app awaits that cancel when recording stops (`Draggable_Recorder_Button.dart`). Not yet checked on a device.
- **Python returns a 500 on a null timing field** in `user_notes`. Rust never sends one and the Dart mapper replaces any null, so it cannot happen today.
- **Two audio-rendering tests fail** in `hum/tests` on a machine without the 148 MB General MIDI soundfont (probably the cause; not confirmed).
- **The app does not send `X-App-Key` yet**, so a production server would reject it. It also still finds the server by mDNS and needs a fixed `https://` address.
- **Not built yet:** Dockerfile, Cloud Run service, moving hum files and score MusicXML off local disk (stateless container), Postgres and R2 accounts.
  For the first release the plan is a single always-on instance so `hum/` needs no change.
- The rebuilt `.a` files are about 63 MB each and tracked in git. Committing them adds that to history each time.
- `build_rs.sh` still uses a global codegen that may not be 2.13.0, and `frontend/ios/libnative_ffi_desktop.a` is stale and unreferenced.
- Nothing has run on a phone or simulator, and the real microphone path (a note with volume crossing the bridge) is untested.
